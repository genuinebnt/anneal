Fundamentalsthe framework, numbers, estimation

01
The delivery framework
16 min

A fixed order for a 45-minute design round, so you never stall and the interviewer always knows where you are: requirements, core entities, API, data flow, high-level design, deep dives. The order is not ceremony: each step produces what the next one needs, and the split between functional and non-functional requirements decides what you draw first and what you spend the deep dives on.

02
Numbers to know
16 min

A handful of orders of magnitude, enough to say whether something fits on one machine, how long a request costs, and whether a cache is worth it. The classic table dates from 2009 hardware, so this page puts it next to numbers measured on a current machine: most ratios held, a few moved, and the slow things are still slow for the same physical reasons.

03
Back-of-envelope estimates
14 min

Rough arithmetic that answers one question at a time: requests a second, storage over years, bandwidth, cache size, servers. The aim is a decision, not a precise figure: each number should end in a sentence that says what it changes in the design.

Core conceptsdata, caching, sharding, replication, APIs

01
Data modeling
20 min

Choosing what to store, how to key it, and which database fits the way it is read and written. In an interview the model is judged by one test: can every hot read and write be served by one lookup or one range scan, at the expected scale, while the rules that must never break are enforced by the database itself.

02
Indexes
17 min

A sorted structure beside a table that turns a full scan into a few page reads, at the cost of slower writes and more storage. Choosing indexes from the queries, reading a query plan, and knowing the special kinds are what separate a design that works on day one from one that works at a billion rows.

03
Caching
24 min

Keeping a copy of hot data in memory, close to where it is read, so most reads skip the slower system behind it. Caches are the cheapest way to cut latency and protect a database, and the source of the hardest bugs: stale data, stampedes and hot keys.

04
Sharding
20 min

Splitting one database's rows across many machines by a key, so writes, storage and indexes grow past what one machine holds. It is the most powerful way to scale a database and the hardest to undo, so it comes after replicas, caching and a bigger machine.

05
Replication
20 min

Keeping copies of the same data on several machines: to survive a machine dying, to serve more reads than one machine can, and to put data near its users. The hard part is not copying; it is what readers see while copies disagree, and what happens when the leader dies.

06
Consistent hashing
15 min

A way to spread keys over servers so that adding or removing one server moves only about 1/N of the keys, instead of almost all of them. Caches, Dynamo-style databases, load balancers and CDNs all rely on it, in one of four variants.

07
Consistency and CAP
18 min

When the network splits, a distributed system either refuses some requests to stay consistent, or answers them all and lets copies disagree for a while. Partitions are rare; the everyday trade is latency against consistency, and it is made per feature, not per system.

08
API styles
20 min

How clients and services talk: REST over HTTP for most product APIs, GraphQL when many clients need different shapes of the same data, gRPC between services. Whatever the style, the same details decide whether an API survives real traffic: what may be retried, how lists page, how errors and limits are reported, and how the contract changes without breaking old clients.

09
Load balancers and API gateways
22 min

The front door of every design: load balancers spread traffic over healthy servers, at the connection (L4) or request (L7) level, and API gateways add authentication, rate limits and routing in one place. Each is replicated so that it is not itself the single point of failure. The choice of algorithm matters more than it looks: on the same servers, the wrong one triples the wait.

10
Unique ID generation
18 min

Every design needs ids: for rows, messages, orders, short links. The choice decides whether ids leak counts, sort by time, fit in 64 bits, and can be made on many machines without coordination, and it shows up later as index size, write speed and how easily the data shards.

Patternsscaling reads and writes, contention, realtime

01
Scaling reads
20 min

Most products read far more than they write, and reads are the easy half: data can be copied as many times as you like, while each write must happen in one place. The moves, in the order to reach for them: make each read cheap, cache the hot set, add read replicas, precompute the answers, and serve what is shared from the edge.

02
Scaling writes
20 min

Reads scale by copying; writes cannot, because each write must land in one authoritative place and be made durable there. When writes outgrow one machine: write fewer, bigger batches, aggregate before writing, buffer bursts through a log, shard by a key, and pick storage built for writes.

03
Dealing with contention
22 min

Many users wanting the same thing at once: the last seat, the last item in stock, the same counter. Contention has two problems in a fixed order: first correctness (exactly one winner, no lost updates), then throughput (one hot row serialises everyone who touches it).

04
Realtime updates
20 min

Getting new data to a client as it happens: polling, long polling, server-sent events or WebSockets on the last hop, and a pub/sub layer behind them when there are many servers. The connection is the easy part; the design questions are what a client missed while it was disconnected and how one event reaches the right million sockets.

05
Queues and streams
22 min

Two ways to hand work from one service to another without waiting: a queue hands each message to one worker and deletes it once that worker acknowledges it; a stream keeps an ordered log that many independent readers move through and can replay. Both deliver at least once, so every consumer must cope with seeing a message twice.

06
Large blobs
20 min

Files, photos and videos do not belong in your database or flowing through your app servers. Clients upload straight to object storage with a presigned URL, in parts that can be retried and resumed, and you keep only metadata, marked ready when storage confirms the bytes arrived.

07
Multi-step processes: sagas, outbox, workflows
24 min

When one business action touches several services (charge the card, reserve the stock, book the courier), there is no single transaction to wrap it. Sagas undo completed steps, the outbox makes 'save and publish' atomic, and workflow engines make the whole thing durable.

08
Resilience: timeouts, retries, circuit breakers
24 min

In a system of many services, something is always slow or down. Timeouts bound the wait, retries with backoff and jitter recover from blips without a storm, circuit breakers stop calling a dependency that is failing, and bulkheads and load shedding keep one problem from sinking everything.

Key technologiesKafka, Redis, Postgres, and how they work inside

01
Kafka
24 min

A distributed, replicated log. Producers append records to the end of a partition; consumers read forward from an offset they keep, so many readers can replay the same history at their own pace.

02
Redis
20 min

An in-memory data structure server: single-threaded command execution over strings, hashes, lists, sets, sorted sets and streams, with optional persistence. Sub-millisecond, and every command is atomic.

03
Postgres
22 min

The default relational database: transactions, joins, constraints and rich indexes, MVCC so readers never block writers, and a write-ahead log that makes commits durable and feeds replicas.

04
Cassandra
24 min

A wide-column store built for writes at any scale: data is spread over a ring of equal nodes by partition key, every write is an append to a log-structured engine, and you choose per query how many replicas must answer.

05
DynamoDB
22 min

AWS's managed key-value and document store: items are found by a partition key and an optional sort key, latency stays in single-digit milliseconds at any size, and you pay for (or provision) reads and writes rather than servers.

06
Elasticsearch
24 min

A distributed search engine on Lucene: documents are analysed into terms and stored in inverted indexes, spread over shards, and ranked by relevance. It is the usual answer for full-text search, filters with facets, and log search, but not for the system of record.

07
Object storage (S3)
20 min

A flat store of immutable blobs addressed by key, priced per gigabyte and per request, built for eleven nines of durability. Every design with files, images, video, backups or a data lake puts the bytes here and only the metadata in a database.

08
etcd and ZooKeeper
20 min

Small, strongly consistent stores replicated by consensus, used to coordinate other systems: leader election, locks with leases, configuration, service discovery and membership. Kubernetes keeps all its state in etcd; older Kafka and HBase used ZooKeeper.

Advanced topicsproximity, vectors, CDC, CRDTs, sketches

01
Proximity search
18 min

Finding what is near a point, fast: drivers within 2 km, restaurants in view. An ordinary index on latitude and longitude cannot do it, so space is cut into cells that an index can.

02
CRDTs and OT
20 min

How several people edit the same document at once and end up with the same text: operational transformation rewrites concurrent edits against each other on a server; CRDTs make edits that commute, so any order gives the same result, even offline.

03
Typeahead and tries
17 min

Suggesting completions as someone types: a trie keyed by prefix with the top results stored at each node, built offline from what people search, served from memory in milliseconds.

04
Probabilistic data structures
20 min

When exact answers need too much memory, a small structure can give a nearly right one with a known error: a Bloom filter for 'have I seen this?', HyperLogLog for 'how many distinct?', a count-min sketch for 'how often?', and heavy-hitter sketches for top-k.

05
Stream processing
20 min

Computing over events as they arrive: counts per minute, joins, alerts. The hard parts are time (events arrive late and out of order), state (kept across millions of keys and restored after failures) and exactly-once results.

Distributed systemsclocks, consensus, quorums, isolation

01
Consensus and Raft
22 min

How a few machines agree on one sequence of decisions even when some crash: elect a leader, replicate a log, and commit an entry once a majority has it. Raft is the version built to be understood; etcd, Consul and Kafka's KRaft run it.

02
Transactions and isolation anomalies
22 min

What can go wrong when transactions run at the same time, and which isolation level stops each problem: dirty reads, lost updates, write skew and phantoms.

03
Storage engines: B-tree and LSM tree
22 min

The two ways databases lay data out on disk. A B-tree updates sorted pages in place and reads fast; a log-structured merge tree appends everything and sorts later, so it writes fast. Knowing which one sits under a database explains most of its behaviour.

04
Quorums, repair and gossip
20 min

How leaderless, Dynamo-style stores stay available and still converge: write to W of N replicas, read from R, make the sets overlap, and repair the differences in the background. Gossip spreads who is alive.

05
Clocks and ordering
20 min

Machines' clocks drift and jump, so a timestamp cannot safely say which of two events happened first. Logical clocks capture cause and effect, hybrid clocks add real time back, and Spanner waits out its clock uncertainty to give a true order.

06
Leases, locks and fencing tokens
18 min

A distributed lock is really a lease: ownership that expires unless renewed. Because a holder can pause and wake up after its lease ran out, safety comes from a fencing token that the protected resource checks, not from the lock alone.

Low-level designSOLID, patterns, concurrency

01
SOLID and design patterns
20 min

The vocabulary of a low-level design round: how classes relate, the five SOLID principles as tests a design should pass, the simplicity principles that keep it small, and the handful of patterns that come up again and again (strategy, observer, factory, state, decorator). Patterns are answers to recurring forces; name the force first and the pattern second.

02
Concurrency primitives
22 min

The tools for correct shared state in a low-level design: mutexes, read-write locks, condition variables, semaphores, atomics and compare-and-swap, plus the classic patterns built from them and the bugs they prevent. Rust's type system rules out data races, but not the race conditions, deadlocks and contention that interviewers ask about; this page runs each of them.

Rustpatterns, async architecture, Rust design questions

01
Design patterns in Rust
20 min

The patterns interviewers expect from a Rust engineer, and how ownership changes them: newtypes and typestate push rules into the compiler, builders replace long constructors, RAII guards replace try/finally, and traits or closures replace class hierarchies. Each program on this page compiles and runs; the lines marked as not compiling were checked to fail with the error quoted.

02
Async Rust architecture
22 min

How a Tokio service is built and what interviewers probe: futures, tasks and the runtime, never blocking the executor, which lock to use, channels for ownership and backpressure, actors, cancellation, and shutting down cleanly. Every program on this page was run with Tokio 1.54.

SQL performance: indexeshow an index is laid out, and what makes a query fast

01
Anatomy of an index
22 min

An index is a second, sorted copy of some columns, kept in fixed-size pages and arranged as a shallow tree, with a pointer from every entry to its row in the table. Everything else in this course follows from that layout: why lookups are fast, why some indexed queries are still slow, and what every index costs a write.

02
Equality, primary keys and checking index use
26 min

A condition `column = value` is the case a B-tree is built for: one descent to the first match, then a short walk along the leaves. Primary keys and unique constraints are such indexes, created for you. Whether the planner uses an index still depends on how many rows match and where they sit in the table, so this module also shows how to check what it chose and why.

03
Multi-column indexes and column order
28 min

An index can hold several columns, sorted by the first and then by the second within each value of the first, the way a phone book is sorted by surname and then by first name. The order of the columns decides which queries the index can serve and how much of it they read: on the example schema the same two columns cost a query 3,116 pages in one order and 23 in the other.

04
Functions, case-insensitive search and bind parameters
27 min

An index on `email` stores email values in email order. A condition on `lower(email)`, `created_at::date` or `customer_id::numeric` asks about a different expression, and the index cannot answer it, however selective the condition. This module shows how to index the expression instead, which functions may be indexed, the ways to search without regard to case, and how a bind parameter's type can quietly do the same damage as a function.

05
Ranges, LIKE and combining indexes
24 min

A B-tree is sorted, so it answers a range as easily as one value: find where the range starts and walk along the leaves until it ends. The walk is cheap. What a range query pays for is the table pages behind the entries it walks over, and that is why a one-day range can cost thousands of page reads while a customer's two months cost nine.

06
Partial indexes and NULL
22 min

Most tables have a small, interesting slice: the pending orders, the unassigned tickets, the rows nobody has processed yet. An index on the whole column spends most of its pages on rows no query asks about. A partial index holds only the slice, and the same idea explains how Postgres treats NULL, which is just the most common slice of all.

07
Conditions that hide a column
20 min

An index can only answer a question asked of the column it sorts. Wrap the column in a function, add a number to it, divide it, coalesce it, or compare it with a parameter that might mean 'anything', and the planner is asked about a different thing: it has nothing sorted to walk and reads the table. The cure is nearly always the same, moving the arithmetic to the other side of the comparison, and the plans show it.

SQL performance: reading plansEXPLAIN, access and filter conditions, statistics, the planner's mistakes

01
Reading EXPLAIN
24 min

A query plan is a tree of small operations, each handing rows to its parent. EXPLAIN prints the planner's guess about that tree; EXPLAIN ANALYZE runs it and prints what happened beside the guess. Reading one is a skill with a short list of rules: which node runs first, what the numbers are per call and in total, where the pages were read, and which gap between guess and reality matters.

02
Access and filter conditions
18 min

Every condition in a WHERE clause is applied somewhere: some steer the index to the right place, some are checked on entries as the index is walked, and the rest are checked on rows after the table was read. The plan prints which is which, and one number, the rows removed by a filter, tells you how much work was thrown away on the way.

03
Statistics: what the planner knows
22 min

The planner never looks at your table when it plans a query. It looks at a small summary kept in the catalog: how many rows, how many distinct values, which values are common, how the rest are spread. Every row estimate in a plan, and so every choice between an index and a scan, is arithmetic on that summary. When a plan is wrong, the summary is usually where to look.

04
When the planner is wrong
20 min

The planner picks the cheapest plan by its own arithmetic, and the arithmetic has two inputs it can get wrong: how many rows it expects (module 10) and what a page or a row costs. This page is about telling those apart, using the planner's own switches as experiments rather than as fixes, and about the places where a plan is wrong by construction: prepared statements and common table expressions.

05
Parallel query
16 min

One query can use more than one CPU core: Postgres starts worker processes, splits a big scan between them and combines their partial answers. It speeds up the queries that read a lot, aggregate a lot or join a lot, and does nothing for the lookups that fill most application code. This page measures what it buys, what it costs and the four ways a query ends up without it.

SQL performance: query shapesjoins, sorting, pagination, subqueries and aggregates

01
Joins: nested loop, hash and merge
20 min

Postgres has three ways to join two tables, and which one it picks decides whether a query takes a millisecond or a second. A nested loop looks up each outer row in the inner table and wants an index. A hash join reads one side into memory and streams the other past it and wants no index at all. A merge join walks two sorted inputs together. This page measures each on the example schema and shows the index each one is waiting for.

02
The N+1 query problem
14 min

N+1 is one query to fetch a list and then one more query for each item in it. It is the most common reason a page that was fast in development is slow in production, and it never appears in an EXPLAIN, because every one of the queries is fast. The cost is in the count. This page measures that cost on a local database, shows the two fixes (a single query with an array, and a lateral join for 'the latest per item') and why a window function is the wrong tool for the second.

03
ORDER BY and GROUP BY from an index
18 min

A sort is the most expensive thing a simple query does, and an index is sorted already. When the order an index keeps matches the order a query asks for, Postgres reads the rows in that order and stops after the first few, so a 'latest 20' query touches 20 rows instead of 2,000,000. This page measures that, then what happens when the order is only partly right (incremental sort), when it is reversed or mixed, where NULLs go, and how GROUP BY uses the same trick.

04
Pagination: OFFSET against keyset
16 min

Page 1 of a list is fast with any method. The difference shows on page 5,000, where OFFSET has to read and throw away every row before the page and the next page costs more than the last. Keyset pagination (also called seek) asks for the rows after the last one you showed and costs the same on every page. This page measures both on 2,000,000 rows, writes the keyset condition correctly with a row-value comparison, and shows the one way to write it that quietly throws the benefit away.

05
Subqueries: IN, EXISTS and NOT IN
15 min

Subqueries have a folklore: EXISTS is faster than IN, joins are faster than subqueries, NOT IN is slow. On Postgres most of that is out of date, because the planner rewrites a subquery in a WHERE clause into a join before it chooses a plan. This page measures the cases: IN and EXISTS produce the identical plan, NOT IN has a correctness trap that matters more than its speed, and a correlated subquery in the select list is a nested loop that is fast or slow for the same reasons any nested loop is.

06
Window functions
15 min

A window function computes over related rows without collapsing them: a running total, the previous order, the first three per customer. The cost is a WindowAgg node that needs its input sorted by the partition and the order, so the plan question is whether that sort comes from an index or from a Sort node, and what the node does to a LIMIT.

07
Aggregates: count, DISTINCT, FILTER, ROLLUP
15 min

count(*) on a big table is slow in Postgres and no index makes it fast: the rows have to be visited, because each transaction may see a different number. This page measures what an exact count costs, what DISTINCT adds, how FILTER turns three scans into one, and what ROLLUP does to the sort.

SQL performance: covering and clusteringindex-only scans, the visibility map, physical order

01
Covering indexes and index-only scans
14 min

An index-only scan answers a query from the index and never visits the table. It is the largest single saving an index can give once the lookup itself is fast, and it is all or nothing: one column missing from the index and the table comes back. This page measures both sides, what INCLUDE is for, and what the extra width costs.

02
The visibility map: when index-only scans lie
14 min

An index entry says a row exists, not that your transaction can see it. Postgres answers that from the table unless a small bitmap, the visibility map, says every row on that page is visible to everyone. VACUUM sets the bits; any write to the page clears them. This page breaks a covering index on purpose and measures the damage and the repair.

03
Physical order: correlation, CLUSTER and BRIN
15 min

A b-tree index is sorted; the table is not. Where the rows that an index returns sit in the table decides how many pages the query reads, and that is a property of the data's physical order, not of the index. This page measures it, reorders a table with CLUSTER, and builds a BRIN index that is 24 kB because it relies on that order.

SQL performance: Postgres internalsrow versions, vacuum, TOAST and the write-ahead log

01
MVCC: row versions, snapshots and bloat
16 min

Postgres never updates a row in place. An UPDATE writes a new version and leaves the old one for transactions that can still see it, and a DELETE only marks the row. That is why readers do not block writers, and it is also why a table that is updated a lot grows, why indexes grow with it, and why VACUUM exists. This page shows the versions directly and measures what they cost.

02
VACUUM, autovacuum and HOT updates
15 min

Dead row versions have to be cleaned up by someone, and that someone is VACUUM. This page reads what one vacuum actually does, measures when autovacuum decides to run (it did not run for 25,000 dead rows and did for 150,000), and shows the two ways to make the work smaller: HOT updates and a lower fillfactor.

03
TOAST: wide values, jsonb and SELECT *
14 min

A Postgres row has to fit in an 8 kB page, so values larger than about 2 kB are compressed, or moved to a side table, before the row is stored. That keeps the main table small and fast to scan, and it makes the cost of a wide column invisible until a query touches it. This page measures a text column and a jsonb document and shows which queries pay for the side table.

04
The write-ahead log, commits and checkpoints
15 min

Every change Postgres makes is first written to a sequential log, the WAL, and a commit returns when that log reaches disk, not when the table pages do. That one design decides what a write costs: how many bytes every index adds, why the first change after a checkpoint is more expensive, and why one transaction per row is slow. This page measures each of them on this machine.

SQL performance: writes and concurrencywhat indexes cost writes, batching, upserts, locks and long transactions

01
What an index costs every write
14 min

Every index is a second copy of some columns that has to be kept in step with the table. A SELECT only ever gains from it, but each INSERT, each UPDATE that creates a new row version, and every delete pays. This page measures what that costs in log bytes, time and disk on a 200,000-row table, with the primary key alone, with one more index and with three more, and shows what HOT updates and VACUUM change.

02
Batching writes: multi-row INSERT, UNNEST and COPY
12 min

Loading 50,000 rows one statement at a time with a commit after each took 14.3 seconds here. The same rows in one COPY took 0.2 seconds, and COPY followed by the index build 0.09. This page measures the steps between: what a commit costs, what a round trip costs, and how much each batching method buys, so you can choose by number instead of habit.

03
Upserts: ON CONFLICT and MERGE
12 min

'Insert it if it is new, update it if it exists' is two statements and a race when written as check-then-write, and one atomic statement when written as an upsert. This page runs both under four concurrent sessions, then measures what an upsert costs when most rows already exist: the dead versions a no-op DO UPDATE leaves, the identity values a conflict burns, and where MERGE fits.

04
Row locks, job queues and deadlocks
13 min

Readers never wait for writers in Postgres, but two writers to the same row do. This page measures what that waiting costs in a job queue, shows the one clause (SKIP LOCKED) that turns the queue from serial to parallel, makes a deadlock on purpose and times how long Postgres takes to notice, and shows the advisory lock for the cases where the thing to lock is not a row.

05
Long transactions and what they block
12 min

A transaction that is open but doing nothing looks harmless. It is not: it can stop VACUUM from removing a single dead row on a table it never touches, and one ALTER TABLE that queues behind it can freeze every query on the table. This page measures both on throwaway tables, and ends with the three timeouts that bound the damage.

SQL performance: special indexesGIN, full text search, trigrams, GiST and vectors

01
GIN indexes for arrays and jsonb
15 min

A b-tree answers 'equal to' and 'between' on one value per row. It cannot answer 'this array contains the tag rare' or 'this document contains plan = pro and region = eu', because the row holds many keys at once. A GIN index inverts the table: for each key, the list of rows that contain it. This page measures what that buys on 500,000 rows, which of the two jsonb operator classes to pick, the queries a GIN index silently cannot serve, and what it costs every insert.

02
Full text search: tsvector, GIN and ranking
15 min

LIKE can find a substring, but it reads every row to do it and knows nothing about words. Postgres has a second kind of text search that does: it reduces each document to a sorted list of normalised words (a tsvector), reduces the query the same way, and answers 'which documents contain these words' from a GIN index. This page measures it on 200,000 documents against LIKE and against the same search done without a stored column, then shows the cost of ranking and what the GiST alternative gives up.

03
Trigrams: LIKE '%x%', typos and nearest names
14 min

A b-tree can answer LIKE 'abc%' because the matches are next to each other in sorted order; LIKE '%abc%' has no such order to walk, so it reads every row. The pg_trgm extension indexes every three-letter piece of each string, which turns the substring search, the case-insensitive one and the 'close to this spelling' search into index lookups. This page measures it on a million titles, shows the pattern lengths where it stops working, and puts the price on each of the three index types.

04
GiST: ranges, nearest neighbours and no double bookings
14 min

A b-tree orders values on a line. Ranges of time, points on a plane and boxes do not fit on a line: two ranges can overlap without either being 'smaller'. GiST is a tree of bounding regions that lets Postgres ask 'which entries overlap this one?' and 'which are nearest?'. This page measures it on a million bookings and a million points, and shows the exclusion constraint, the one feature that makes the database refuse overlapping rows.

05
pgvector: nearest neighbours, HNSW and IVFFlat
12 min

A vector index answers 'which stored points are nearest to this one?' by giving up exactness: it can miss a true neighbour, and you tune how often against how fast. This page explains the vector type, the three distance operators, how HNSW and IVFFlat work and what each knob trades. It is a concepts page: pgvector was not built in the environment that wrote it, so nothing here was measured.

SQL performance: at scalePartitioning, materialized views, pooling and replicas

01
Partitioning: what it speeds up and what it only moves
14 min

Declarative partitioning splits one big table into many smaller ones by a key, usually time. It is often proposed as a speed-up for big tables. This page measures what it does to queries (less than people expect when an index exists, a lot when it lets Postgres skip most of the data), what breaks the skipping, what it costs (one extra index scan per partition, a primary key that must contain the partition key) and what it is genuinely good at: removing old data without a DELETE.

02
Materialized views: precompute, then manage the staleness
12 min

A dashboard that sums two million orders by month does the same two seconds of work on every page load. A materialized view stores the result of that query as a table, so the page reads a few thousand rows instead. What you buy is speed; what you pay is that the stored answer is as old as the last refresh, and that refreshing it has its own cost and its own locking. This page measures all four: the speed-up, the staleness, the refresh time, and which refresh blocks readers.

03
Connections and pooling: how many is too many
12 min

Every Postgres connection is a server process. Opening one costs far more than running a short query, and having many open at once does not make the database faster, because the CPU cores it runs on stay the same. This page measures both with pgbench on a four-core machine: the price of connecting for every query, and how throughput and latency change as the number of concurrent clients goes up. That is the argument for a connection pool, and for keeping its size small. PgBouncer itself was not installed here, so what a pooler changes in practice is argued from these numbers and the documentation, not measured.

04
Read replicas: lag, stale reads and query conflicts
12 min

A read replica takes read traffic off the primary, at a price that every design has to state: it is behind. This page builds a real streaming replica of the test database on the same machine and measures how far behind it is when idle and under a heavy write load, what happens to a read that immediately follows a write, and the two ways a long query on a replica can go wrong: being killed by the primary's cleanup, or holding the primary's cleanup back. The numbers come from loopback on one machine, so network lag is not in them.

SQL performance: from Rustsqlx, plan assertions in tests and monitoring in production

01
sqlx from Rust: binds, statement cache, pool size and plan assertions
14 min

The earlier modules measured the database. This one measures the client: what sqlx does with a query on its way to Postgres, whether its prepared-statement cache earns anything on a fast lookup, how the size of the connection pool changes throughput, and what batching is worth from Rust. It ends with a test that fails when a query's plan gets worse: an EXPLAIN assertion you can put in your test suite so that dropping an index, or a change that makes the planner sort, fails in CI instead of in production.

02
Monitoring: finding the slow query in a running system
14 min

Everything so far assumed you knew which query to look at. In a running system you do not: you have a database that feels slow and thousands of statements. Postgres can tell you which ones cost the most, show the plan of a slow one as it happened, say what a stuck session is waiting for, and list the indexes nobody uses. This page runs each tool on the test database and shows what it reports, including the answer that is easy to get wrong: the query that matters is not the one that runs most often, and not necessarily the slowest.

SQL performance: other enginesSQLite, measured against the same indexing rules

01
SQLite: the same indexing rules in an embedded engine
12 min

SQLite is a database in a library: no server, no network, one file. The indexing lessons of this course hold there with different words: a scan, a search using an index, a covering index. What differs is where the time goes: a lookup is a function call, not a round trip, and a commit is a file sync, which makes the way you commit the biggest performance decision. This page repeats the key measurements of the early modules on SQLite 3.53.1 (the version in this environment's Python) and shows its EXPLAIN QUERY PLAN.

SQL performance: referenceMyths checked against plans, the example schema and a glossary

01
Myths: five rules of thumb, checked against real plans
12 min

Database advice travels as one-line rules. Some are right for a reason, some were right once, and some never were. This page takes five common ones and runs each on the test database (2,000,000 orders, Postgres 18.6) to see what the plan and the buffer counts say. For each the verdict is stated narrowly: what is true, and under what condition.

The example schema
5 min

Most pages in this course run on the same small shop: customers, products, orders and order items, generated with a fixed random seed so every plan can be captured again. This page lists the tables, their sizes and the data's shape, as they are in the database the plans were captured from (Postgres 18.6).
